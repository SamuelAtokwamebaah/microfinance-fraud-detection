# Data dictionary

Eight tables, generated by `src/generate.py` from the single seed in `src/config.py`.
Row counts below are from the published seed and are reproducible exactly.

**All data is synthetic.** No real borrower, credit officer, branch or institution is
represented, and no data from any real engagement was used.

## The three layers

The whole project turns on one separation, and reading the dictionary without it will
be confusing:

| Layer | Table | Who may read it |
|---|---|---|
| What the borrower was **contracted** to pay | `repayment_schedule` | detection ✓ |
| What the **books** say arrived | `repayments_recorded` | detection ✓ |
| What **actually** happened at the doorstep | `ground_truth_repayments` | **evaluation only** |

Detection code in `sql/` and the dashboard read the first two. Only `src/evaluate_tier1.py`,
the evaluation half of `src/tier2.py`, and the evaluation panel of the dashboard read the
third. In real life nobody can see the third layer either, until somebody asks a borrower.

## `branches` — 5 rows

| Column | Type | Description |
|---|---|---|
| `branch_id` | INTEGER | Primary key |
| `name` | TEXT | Synthetic branch name, drawn from Ghanaian place names |
| `region` | TEXT | Greater Accra, Volta or Eastern |
| `opened_date` | TEXT | ISO date, 3–10 years before the observation window |

## `credit_officers` — 20 rows

Four officers per branch, each carrying 150 borrowers.

| Column | Type | Description |
|---|---|---|
| `officer_id` | INTEGER | Primary key |
| `branch_id` | INTEGER | → `branches.branch_id` |
| `name` | TEXT | Synthetic: a given name plus one initial, deliberately non-identifying |
| `hired_date` | TEXT | ISO date |
| `owns_followup` | INTEGER | 1 when the officer also owns delinquency follow-up on his own book. **This is the control failure the project is about**: no independent party ever contacts a borrower the officer has marked delinquent. Set by `INDEPENDENT_FOLLOWUP` in config |

## `borrowers` — 3,000 rows

| Column | Type | Description |
|---|---|---|
| `borrower_id` | INTEGER | Primary key |
| `officer_id` | INTEGER | → `credit_officers.officer_id`. The officer who owns the relationship |
| `branch_id` | INTEGER | → `branches.branch_id` |
| `name` | TEXT | Synthetic, same convention as officers |
| `enrolled_date` | TEXT | ISO date. Tenure matters: the scheme selects long-tenured borrowers |
| `occupation` | TEXT | Market trader, seamstress, carpenter, farmer, and similar |
| `income_band` | TEXT | `low`, `medium` or `high`. Caps the principal a borrower can take |
| `is_market_trader` | INTEGER | 1 for weekly-cash-cycle borrowers, who repay more erratically. **Not decoration**: a detector that cannot tell a trader having a bad market week from an officer skimming will drown in false positives |

## `loans` — 3,877 rows

| Column | Type | Description |
|---|---|---|
| `loan_id` | INTEGER | Primary key |
| `borrower_id` | INTEGER | → `borrowers.borrower_id` |
| `officer_id` | INTEGER | → `credit_officers.officer_id`, denormalised for query convenience |
| `principal_ghs` | REAL | GHS 500–20,000, capped by income band |
| `interest_method` | TEXT | `flat` (70%) or `declining` (30%). Flat charges interest on the original principal for the whole term regardless of repayment, and is the common microfinance product |
| `annual_rate` | REAL | 0.24–0.48 |
| `term_months` | INTEGER | 3, 6, 9, 12, 18 or 24 |
| `frequency` | TEXT | `weekly` (65%) or `monthly` (35%) |
| `disbursed_date` | TEXT | ISO date |
| `status` | TEXT | `active`, `closed` or `defaulted` |
| `restructured_from_loan_id` | INTEGER | → `loans.loan_id`, nullable. Reserved; unused at v1 |

## `repayment_schedule` — 144,542 rows

What the borrower was contracted to pay. One row per installment.

| Column | Type | Description |
|---|---|---|
| `schedule_id` | INTEGER | Primary key |
| `loan_id` | INTEGER | → `loans.loan_id` |
| `installment_no` | INTEGER | 1-based position within the loan |
| `due_date` | TEXT | ISO date |
| `amount_due_ghs` | REAL | Constant across a loan's installments |

## `repayments_recorded` — 136,578 rows

What the books say arrived. **An installment with no row here was either never paid or fully
skimmed, and the two are indistinguishable from this table alone** — which is the point.

There is deliberately no "outstanding balance" column. Balance is derived from schedule minus
recorded, so withholding a payment inflates the balance automatically, exactly as it did in the
real ledger.

| Column | Type | Description |
|---|---|---|
| `repayment_id` | INTEGER | Primary key |
| `loan_id` | INTEGER | → `loans.loan_id` |
| `schedule_id` | INTEGER | → `repayment_schedule.schedule_id` |
| `officer_id` | INTEGER | The officer who recorded it |
| `recorded_date` | TEXT | ISO date, may be after `due_date` for a late payment |
| `amount_recorded_ghs` | REAL | May be **less** than `amount_due_ghs`: an honest short payment, or a partial skim. Measured on the published seed, 6.4% of recorded installments are honest shortfalls |
| `channel` | TEXT | `cash_to_officer` (78%), `branch_counter` (15%), `mobile_money` (7%) |

# Ground truth — evaluation only

**Detection code must never join to these tables.** They exist so that precision and recall
can be measured, and they are the reason those figures mean anything.

## `ground_truth_officers` — 20 rows

| Column | Type | Description |
|---|---|---|
| `officer_id` | INTEGER | → `credit_officers.officer_id` |
| `is_fraudulent` | INTEGER | 1 for the injected schemes. Two officers at the published seed |
| `scheme_type` | TEXT | `unrecorded_repayment_skimming`, or NULL |
| `active_from` | TEXT | When the scheme begins, `FRAUD_START_MONTH` into the window |
| `active_to` | TEXT | End of the observation window |
| `peak_intensity` | REAL | `SKIM_PROBABILITY` at full ramp |

## `ground_truth_repayments` — 144,542 rows

One row per scheduled installment, including the honest ones, so the table can be joined
without dropping rows.

| Column | Type | Description |
|---|---|---|
| `schedule_id` | INTEGER | → `repayment_schedule.schedule_id` |
| `loan_id` | INTEGER | → `loans.loan_id` |
| `actually_paid_ghs` | REAL | What the borrower really handed over. 0 for a genuine miss |
| `actually_paid_date` | TEXT | ISO date, NULL when nothing was paid |
| `was_skimmed` | INTEGER | 1 where an officer withheld part or all of a payment |
| `skimmed_amount_ghs` | REAL | The amount withheld. `actually_paid_ghs` minus this equals what reached the books |

## Reading the fraud from the tables

For a skimmed installment, the three layers diverge like this:

```
repayment_schedule.amount_due_ghs      28.26   the contract
ground_truth_repayments.actually_paid  28.26   the borrower paid in full
repayments_recorded.amount_recorded    17.98   the books show a shortfall
ground_truth_repayments.skimmed_amount 10.28   the difference, taken
```

The borrower believes he is current. The book shows him falling behind. Nobody
reconciles the two, because the officer who recorded it is also the officer who
would chase the arrears.
